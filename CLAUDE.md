## Язык

Все коммуникации и комментарии — **на русском языке**. Сохранять диакритические знаки полностью корректно. Технические идентификаторы (имена функций, переменных, классов) — на английском.

## Plan → Do → Verify (главное правило)

Любая задача = три шага:

1. **ПЛАН** — разобраться в задаче, определить критерии проверки, для крупных задач — задать 5-20 уточняющих вопросов и согласовать план.
2. **ВЫПОЛНЕНИЕ** — следовать плану, при изменениях — обновлять план, не уходить в сторону.
3. **ПРОВЕРКА** — перед "готово" перечислить что проверено: "Проверил: X ✓, Y ✓, Z ✓".

**Без проверки задача не считается готовой.** Подробнее — [`rules/plan-do-verify.md`](rules/plan-do-verify.md).

## Критические архитектурные правила AICheck

### 🔴 1. Анонимизация PII перед AI-вызовами

В Mathpix, OpenAI (GPT-5.4 / GPT-5.4 mini), Anthropic Claude, Gemini — **никогда не отправлять**:
- ФИО, имя/фамилию ученика или родителя
- Email, телефон, паспортные данные
- Любые другие персональные идентификаторы

Использовать `pseudo_id` (UUID), хранимый в `User`, и контент задания/работы. Реализация — `apps/api/app/services/ai/anonymizer.py` (Chunk 7).

**Snapshot-тесты обязательны** — доказывают отсутствие PII в payload AI-вызовов.

**Why:** требование 152-ФЗ (локализация ПДн в РФ с 1 июля 2025). Хостинг AI-сервисов в США. Нарушение = штрафы до 18 млн руб + блокировка.

### 🔴 2. Style contract для AI-комментариев ученикам

Все комментарии, генерируемые GPT-5.4 для отправки ученику, **должны проходить style_contract** (`apps/api/app/services/ai/prompts/style_contract.py`):

- ЗАПРЕЩЕНО: "Молодец что попробовал", "Отличная работа", "Я заметил, что...", "Хочется отметить", "Прежде всего", "В целом", эмодзи, восклицательные знаки.
- РАЗРЕШЕНО: прямой указ на ошибку и краткая рекомендация.
- Максимум 2-3 предложения.

Snapshot-тесты на 50+ примерах — обязательны.

**Why:** комментарий не должен выглядеть AI-сгенерированным. Это критично для UX: учитель и ученик должны верить, что обратная связь от человека.

### 🔴 3. Pseudonym-only ученики (без ФИО)

При создании `StudentProfile` — поле `display_name` принимает только псевдоним ("Иван И.", "Маша 7А"). **Не запрашивать ФИО, паспорт, дату рождения.**

**Why:** это обходит требование отдельного письменного согласия родителей (с 01.09.2025) и сильно повышает конверсию онбординга. Email родителя — опциональное поле с галочкой согласия на отчёты в обычной оферте.

### 🟢 4. Двухуровневый AI-анализ

Pipeline проверки работы:
1. **OCR** через `OCRProvider` (выбор фиксируется в Chunk 7 после валидации на 50 работах).
2. **Extract errors** — GPT-5.4 mini, structured JSON: `{errors[], tags[], score_draft}`.
3. **Generate feedback** — GPT-5.4, лаконичный комментарий 2-3 предложения с применением style_contract.
4. **Fallback** — Claude Sonnet 4.6 при сбое любого шага.

OpenAI и Anthropic API — **только через зарубежного посредника пользователя**. Прямой OpenAI API недоступен из РФ.

## Workflow разработки

### Git
- Каждый чанк — feature-branch `chunk/NN-name`.
- Коммиты — после каждого логически осмысленного изменения.
- Push — часто (не накапливать).
- Merge в `main` — только после прохождения критериев готовности чанка из плана + одобрения PR пользователем.
- НИКОГДА не амендить опубликованные коммиты, не делать force push в main, не обновлять git config без разрешения.

Подробнее — [`docs/workflows/git-workflow.md`](docs/workflows/git-workflow.md).

### Дизайн-референсы для UI-чанков

Для **Chunks 4, 5, 6, 9, 10, 11, 13** (UI-чанки) — **обязательно запросить у пользователя дизайн-референсы ДО начала разработки**:
- Скриншоты сайтов
- Figma-макеты
- Конкретные блоки/компоненты для подражания
- Пожелания по UX (что на одном экране, что в модалках)

Если референсов нет — предложить 2-3 варианта на выбор через AskUserQuestion с ASCII-mockups.

Подробнее — [`docs/workflows/design-references.md`](docs/workflows/design-references.md).

### Использование skills

Активно использовать готовые скиллы Claude Code:
- `commit` — автокоммит после логических блоков
- `code-reviewer` — независимое ревью перед merge feature-branch
- `qa` — генерация и запуск тестов перед approve чанка
- `frontend-design` — для UI-чанков (4-13)
- `feature-dev:feature-dev` — guided feature development

Custom skills проекта — в [`.claude/skills/`](.claude/skills/).

### Использование agents

Для крупных задач делегировать subagents:
- `feature-dev:code-explorer` — понять архитектуру перед изменениями
- `feature-dev:code-architect` — спроектировать blueprint фичи
- `feature-dev:code-reviewer` — независимое ревью с фильтром high-confidence issues
- `research` — обязательно вместо прямых WebSearch/WebFetch

Custom agents проекта — в [`.claude/agents/`](.claude/agents/).

## Правила кода

### Python (apps/api)
- Python 3.12+, использовать `python3` (не `python`)
- Зависимости — через `pip` в `requirements.txt`
- Линтер — `ruff`, типы — `mypy --strict` для `app/services/`
- Async везде где возможно (`asyncio`, `aiohttp`, `aioboto3`, `asyncpg`)
- Всегда после изменения `.py` — `python3 -m py_compile <file>` для синтаксиса

### TypeScript (apps/web)
- TypeScript strict mode, ESLint + Prettier
- Тип-генерация из OpenAPI: `pnpm exec openapi-ts` после изменений в `apps/api`
- Компоненты — функциональные, hooks-based, server components где возможно
- shadcn/ui — добавлять компоненты через `pnpm dlx shadcn-ui@latest add`

### YAML / JSON
- После изменений `.yaml` — `python3 -c "import yaml; yaml.safe_load(open('файл'))"`
- После изменений `.json` — `python3 -c "import json; json.load(open('файл'))"`

### Безопасность
- Никаких секретов в коде, только в `.env` (gitignored)
- НЕ создавать SQL-запросы конкатенацией строк (только параметризованные)
- НЕ использовать `eval`, `exec`, `pickle` на пользовательских данных
- Валидация всех входных данных через Pydantic schemas

## Проверка результатов работы

**После каждой задачи** — перечислить что проверено. Не "всё ок", а конкретно:

> "Проверил: ruff ✓, mypy ✓, pytest 12 passed ✓, миграция применена ✓, нет секретов в коде ✓"

Для важных задач (анонимизатор, AI-промпты, юридические страницы) — запускать subagent `reviewer` для независимой проверки с чистым контекстом.

Подробнее — [`rules/always-verify.md`](rules/always-verify.md).
